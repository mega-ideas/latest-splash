## 1. Signing in

There is no shared demo account. Phase 3 made signing up grant *nothing* —
`resolveAuthorityForSession` throws rather than provisioning a membership — so a
fresh database has no account that can open the dashboard. That is correct, and
it means the account has to be created deliberately.

```bash
npm run seed:demo -- --kyb ACTIVE
```

That writes three rows (`organizations`, `users`, `memberships`) and prints what
it set:

| | |
|---|---|
| **Email** | `demo@acme.test` |
| **Password** | `SplashDemo!2026` |
| **Workspace** | `demo-business` — Acme Manufacturing |
| **Role** | `admin` (can prepare *and* approve) |
| **KYB** | `ACTIVE` |

Then sign in at `/login`. Verified end to end on 6 Sep: typed into the real form,
lands on `/dashboard`.

**Flags worth knowing:**

- Omit `--kyb ACTIVE` and you get `REGISTERED`, which is the honest default — a
  real new business starts there, money movement is blocked, and it is the only
  way to exercise the KYB gate.
- `--email`, `--password`, `--org`, `--role`, `--org-name` all override.
- It **refuses to run against a non-local `DATABASE_URL`** without `--force`. A
  seeded account with a published password is precisely what must not exist in a
  deployed cluster.

`role` matters: `admin` can prepare and approve, but the same person being maker
*and* checker on one proposal is still refused. To walk the full maker-checker
path you need two accounts:

```bash
npm run seed:demo -- --kyb ACTIVE --email maker@acme.test --role maker
npm run seed:demo -- --kyb ACTIVE --email checker@acme.test --role checker
```

### Running it

```bash
npm run dev
```

You need Postgres on the URL in `.env.local` (currently `127.0.0.1:5433`) with
migrations applied — `npm run db:migrate`, or apply `drizzle/*.sql` in order.
There are **17 migrations**; two are new in this round (`0015`, `0016`).

## 2. What changed

Six commits. The through-line: **several screens were asserting things they had
not read**, and three of those turned out to be security or correctness bugs
rather than the cosmetic problems they looked like.

### `e6c5498` — 0xWal: three chat surfaces, two agents

There were three chat UIs and two agents. The desk used `/api/oxwal` (real, with
read/propose tools and an approval path). The copilot page and floating widget
used `/api/copilot/chat` — no tools — and **when that failed they fell back to a
local keyword matcher.**

Asked "what is the PHP rate", that fallback answered `56.42` from a string
literal, in the same bubble and tone as a real quote. The invented answers were
the *fallback*: the path taken exactly when the real system was unreachable.

- One engine (`lib/oxwal/use-oxwal-thread.ts`), one renderer
  (`components/oxwal/ThreadView.tsx`), used by all three surfaces.
- `/api/copilot/chat` and `lib/copilot-client.ts` **deleted**, not left
  orphaned. A second tool-free agent sitting there for someone to wire up next
  month is how this came back three times.
- Found in the surviving agent: `"Compliance posture: KYB Tier 1 approved, AML
  clear, no sanctions flags"` — asserted to any caller, including accounts with
  no KYB at all. `lib/agent/oxwal.ts` was never in the canned-claims guard's
  file list. Now it is.
- Also found: `meta` announced `source: 'claude'` *before* the first token, then
  fell back to the local planner without correcting it. `meta` now says
  `attempting`; a `done` frame states who actually answered.
- Renaming the assistant wrote to MemWal and **nothing read it back**. Now it
  reaches the system prompt and the UI. The AI label is a separate element from
  the name, so a rename to "Sarah" cannot remove it from a payment
  recommendation.
- "Good morning" used to get the same refusal as "what is the bitcoin price".
  `DAILY_TALK` answers ordinary things warmly and claim-free; external lookups
  are still declined, because there is no tool that reaches outside Splash.

### `c9d0baf` — WhatsApp approval had a server and no way in

`/api/approvals/channel` and the `approvalChannel` / `whatsappEnabled` settings
existed and **nothing in the product called any of them**. An approver could not
register a number, so no approval request could reach anybody.

New settings section. The two modes are not fast-versus-slow — they authenticate
different things, and that sentence now sits beside each option:

- **One-time code** (default) — needs the handset *and* a signed-in approver
  account. A stolen phone alone releases nothing.
- **Reply APPROVE** — proves possession of a handset, not the identity of a
  person. Whoever holds the phone can release the payment. Marked *Weaker*.

A number is inert until a code sent *to* it comes back, because the failure mode
of a mistyped digit is silence: the approver is simply never asked.

### `99bb67d` — KYB cases (security)

Two customer-facing reads were authenticated but **not scoped**:

- `GET /api/kyb/cases/[id]` returned any case to any signed-in user.
- `GET /api/kyb/cases/latest` took `businessName` from the **query string** and
  matched it against every case in the process.

The second is the serious one: pass a competitor's name, receive their KYB file
— registration number, the name and SHA-256 of every document they uploaded, the
reviewer's notes, the rejection reason. A business name is not a secret.

`/latest` now takes no parameter at all; the session says who is asking. `/[id]`
answers 404 rather than 403 for someone else's case, so it is not an id oracle.
Staff reads are spelled `*ForStaff`.

Separately: `recordKybSubmission` defaulted to `orgId ?? 'demo-business'` and the
upload route never passed one — so **every new business's KYB case was filed
into the demo workspace**. Same defect class as the zkLogin one fixed earlier.
They get their own workspace now, created in `REGISTERED`.

Migration `0015`. Unique on `(org_id, registration_number)`, not on registration
number alone — those are only unique within a registry.

### `3f3a685` — the first screen after sign-in was invented

Almost nothing on `/dashboard/overview` came from anywhere: `$39,120` 30-day
volume, an `8 authorized / $4,540` pipeline, six fake transactions with ids
shaped like real ones (`ti_m8q4_9b21fa`), `"Acme Trading Sdn Bhd"` as everyone's
company name, and a Compliance panel reading:

> KYB status: **Approved · Sumsub verified** · Risk tier: **Tier 1 · Low risk**

rendered identically for an organisation in `REGISTERED` that cannot move a
dollar.

Now read from `/api/kyb/state`, `/api/transfers` and `/api/settings`. Pipeline,
recent list and 30-day volume all derive from **one** read, so three panels
cannot disagree. Empty desks say so, distinguishably from still-loading.

The corridor table keeps its figures — its headers already say *Model volume*
and *Test success*, and a labelled projection is not a lie. A test now holds
those labels in place so they cannot quietly go while the numbers stay.

**Verified live on 6 Sep** with `FEATURE_KYB_GATE=true`: an unverified account
now shows *"Not started — complete business verification"* and *"Blocked until
verification completes"*, where it previously said Approved.

### `8bb6243` — treasury persistence (correctness)

Balances, withdrawal notices and the yield accrual baseline all lived in module
state.

1. A restart zeroed every customer's balance.
2. It dropped every PENDING withdrawal notice. A notice is an obligation —
   funds are reserved out of treasury immediately and the settlement cron reads
   that list. A restart in between left money reserved with nothing scheduled to
   release it, and no record it was owed.
3. **Every deploy silently skipped a day of yield.** Yield is a price delta, so
   accrual needs the previous NAV. That baseline was a module-level `let`; a
   null baseline correctly records nothing, which is right on the first run ever
   and wrong on the first run after every deploy. No error, no log.

Migration `0016`. `bigint` columns, a `CHECK` refusing negative balances (the
mover is not the only writer — accrual writes too, and a falling price produces
a negative delta by design). The demo seed stays on the memory backend and is
never written to Postgres: a fixture on a real ledger is money that does not
exist.

### `app/error.tsx` — no error boundary existed

There was an `app/loading.tsx` and **no `error.tsx` anywhere in the tree**, so a
server component that threw left the loading screen on screen indefinitely. A
spinner is a promise that something is still happening; a customer watching one
waits, reloads, and never learns nothing is coming.

It shows the `digest` (the id matching the server log), never `error.message` —
a server exception can carry a query or a row, and this renders for customers.

## 3. Environment variables

Nothing below is required for the code to run; each unlocks a feature.

```bash
# KYB gate — off by default. With it off, readKybGateState returns ACTIVE
# unconditionally and the compliance panel cannot be meaningfully tested.
FEATURE_KYB_GATE=true

# zkLogin — three variables, not one. No client secret: the flow uses
# response_type=id_token, so nothing secret sits in the front end.
FEATURE_ZKLOGIN=true
ZKLOGIN_GOOGLE_CLIENT_ID=...      # Google Cloud Console → OAuth client (Web)
                                  # redirect: {origin}/login/zklogin/callback
ZKLOGIN_USER_SALT=...             # ours, generated once. NEVER rotate — it
                                  # changes every derived address.

# WhatsApp approvals (Twilio sandbox is enough to demo)
TWILIO_ACCOUNT_SID=AC...
TWILIO_AUTH_TOKEN=...
TWILIO_WHATSAPP_FROM=+14155238886
TWILIO_WEBHOOK_URL=https://<public>/api/webhooks/whatsapp

# Sumsub webhook (verified before the body is parsed; no secret = refuse)
SUMSUB_WEBHOOK_SECRET=...

# The model 0xWal runs on. Defaults to Haiku 4.5; the env var raises it
# without a deploy.
ANTHROPIC_API_KEY=...
ANTHROPIC_MODEL=claude-haiku-4-5-20251001
```

Without `ANTHROPIC_API_KEY` the agent runs its deterministic local planner and
the `done` frame reports `local` or `scripted` — honestly, which is the point of
that change.

## 4. For Sebastian

**Nothing here needs your sign-off to merge** — no Move, no contract config, no
key material. These are the parts worth your eyes anyway:

1. **The two scoping bugs** (`99bb67d`). Both were "authenticated but not
   authorised". If that pattern exists anywhere in SplashAN's routes, it is
   worth the same sweep: `requireCustomerRequest` proves *who*, and says nothing
   about *whose data*.

2. **`/api/kyb/state` is new** and client-readable. It returns
   `{ state, blocked, reason }` for the session and gates nothing — the money
   routes enforce the gate themselves. If you add a surface that needs KYB
   standing, use this rather than re-deriving it.

3. **Migrations 0015 and 0016** must be applied before this branch runs against
   an existing database. `drizzle/meta/_journal.json` lists all 17;
   `npm run lint` fails if a migration is unjournalled, because `drizzle-kit
   migrate` reads the journal and not the directory.

4. **`listKybCases` and `getLedger` changed signature** — both now require an
   org and are `async`. If SplashAN has callers, the type system will find them;
   that is how all eight were found here.

5. **The accrual baseline is now a database row.** If you run the accrual cron
   against a database that has never had it, the first run establishes the
   baseline and records nothing. That is correct and expected — not a bug.

### Still open

- **KYB case *documents*** are metadata only in Postgres; the files themselves
  remain behind `storageKey` and that storage is not implemented.
- **Daily-limit *usage*** is not computed anywhere. The overview states the
  limit and deliberately does not claim a percentage used.
- **WhatsApp reply mode** is built but has only been exercised against the
  signature verifier, not a live Twilio round trip.
- **zkLogin** is wired and dark until the three env vars are set.

## 5. One thing not to re-chase

I reported earlier that dashboard routes did not hydrate — only `<head>`
attached, the loading overlay stuck, clicks did nothing. **That was wrong, and
there is no hydration bug.**

The cause was the local Postgres shim (`@electric-sql/pglite-socket`) used for
verification. It serves one connection and resets it under load. When it reset,
every DB read failed with `ECONNRESET`, the dashboard layout could not resolve,
and the page never hydrated. My A/B test — restoring the original files and
seeing the same failure — correctly proved it was not *my code*, but I drew the
wrong conclusion from it, because the shim was the constant in both runs.

With a healthy database: **353 hydrated elements on `/dashboard`**, the composer
chips work, and the agent answers in the thread. Verified 6 Sep.

If you see the symptom again, check the database before the client. It looks
exactly like a hydration failure and is not one — which is the reason
`app/error.tsx` now exists.
